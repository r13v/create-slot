# Failure isolation

Every **declared** contribution is wrapped in an error boundary and a `Suspense`
boundary, placed by the host. That isolation is the host's job, not the
contribution author's: a plugin comes from somewhere else, and the application
is the one that has to stay up.

Failure is the host's business. Pending UI is not: the `Suspense` boundary uses
`fallback={null}`, so add an inner `Suspense` when the contribution needs a
visible pending state. See [splitting a declared
contribution](/recipes#splitting-a-declared-contribution).

## On the client

The boundary catches, `renderFailed` renders in place of the contribution, and
`onError` reports it.


`onError` receives the `pluginId`, the slot name and the error, which is enough
to attribute a failure to a feature without the feature cooperating.

| prop | when it runs | what it gets |
| --- | --- | --- |
| `onError` | once, when the boundary catches | `{ pluginId, slot, error }` |
| `renderFailed` | on every render while the boundary holds an error | the same, plus `reset` |

Both live in a context of their own, read only where a contribution is isolated,
so writing them inline — which is how everyone writes them — never re-renders a
host. See [Performance](/performance#keep-the-plugin-list-stable).

### What a boundary does not catch

The boundary is React's, so its limits are React's. It catches errors thrown
**during render**, in a lifecycle method, or in a constructor below it. It does
not catch:

- an error thrown in an event handler — `onClick`, `onSubmit`, and the rest;
- a rejected promise that nothing awaits inside render;
- an error thrown inside `setTimeout` or an effect's async continuation;
- anything thrown by the host or the layout itself, which is above the boundary.

A contribution that does async work handles its own failures, or throws during
the next render so the boundary can see it.

## On the server

`getDerivedStateFromError` never runs during a server render, so the class
boundary cannot catch there. The `Suspense` boundary still does its job:

1. React marks just that boundary for a client render — `<!--$!-->` in the HTML.
2. The rest of the markup is kept and sent.
3. The client re-renders that one contribution, where the class boundary
   finally catches it and `renderFailed` takes over.

One broken contribution costs its own line, not the page. This holds for both
`renderToString` and `renderToPipeableStream`.

## There is no automatic reset

Recovery is the explicit `reset()` handed to `renderFailed`, and nothing else.

Resetting on element identity would loop: a host that re-renders in response to
`onError` produces a fresh element every time, so the boundary would clear,
throw, clear, throw. The boundary sits directly around the contribution in the
same commit, so React's own behaviour is enough — a button is the honest
alternative to a loop.

## Runtime fills get only `Suspense`

A host wraps each runtime fill in `Suspense` with a `null` fallback. This is a
safety boundary: without it, a suspended host can hide the subtree that
registered the fill, remove that registration, reveal it and repeat forever.

There is still no error boundary or plugin identity. A fill is your own code in
your own tree, not a third party's contribution, so failure isolation remains
yours. Add an inner `Suspense` when the pending state needs visible UI.

that — its crash-test feature ships one, because the runtime channel leaves
errors to you.
