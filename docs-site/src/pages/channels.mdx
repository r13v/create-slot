# Two channels

A contribution reaches a host in one of two ways, and the two differ in what a
contribution *is*. Everything else — whether it appears in server HTML, whether
one feature's contributions can share `useState`, whether an error boundary
wraps it — follows from that.

## The short answer

**Declarative for anything that must be in the HTML. Runtime for chrome that
depends on live tree state.**

If one question decides it, it is this: *does the contribution have to exist
before hydration?* Navigation, above-the-fold content, anything a crawler reads,
anything whose late arrival shifts the layout — declarative. A status entry that
exists only while a dialog is open, a badge a row puts up about its own
selection — runtime.

When neither applies, prefer declarative. It is the primary channel, it costs
nothing extra, and it is the one that keeps its options open.

The rest of this page is why.

## Declarative: data plus a component

`slot.contribute()` produces a plain object: a slot name, an `order`, and a
component. A plugin carries a list of them, and the provider builds an index
from the plugin array **during render**.

Because the index is built during render, a host can enumerate its
contributions synchronously — which is exactly what a server render needs. This
is the primary channel.

## Runtime: an element from where it is mounted

`slot.Fill` renders nothing where it sits. It registers its child element into
the slot for as long as it is mounted, and every mounted host for that slot
renders it.

```tsx twoslash

// ---cut---
// [!include ~/snippets/channels-guide.tsx:runtime]
```

`createSlot` is a façade over exactly this: `createSlot()` is `defineSlot`
under a generated name, and the `Slot` it returns *is* the `Fill`.

This channel cannot reach server markup. Registration happens in an effect —
the only honest moment, since the host has already rendered by the time a fill
elsewhere in the tree gets to announce itself.

## The comparison

| | Declarative | Runtime |
| --- | --- | --- |
| A contribution is | data plus a component | an element |
| Registered | during render, from the plugin list | from an effect, while mounted |
| In server HTML | **yes** | no |
| Needs `PluginProvider` | yes | no |
| Stored in | the provider's index | a module-level store |
| Error + `Suspense` boundary per contribution | placed by the host | none — bring your own |
| One feature's contributions share `useState` | no — they are separate subtrees | yes — one subtree |
| Reads host props via | its own props | `useProps()` |
| Turning a feature off | filter the plugin array | stop rendering it |

## What each choice costs

Reach for the declarative channel when the contribution is navigation,
above-the-fold content, anything a crawler reads, or anything whose absence
during hydration would shift the layout. You get server rendering, streaming
and per-contribution failure isolation, and you pay for it by giving up the
shared React subtree: a plugin's contributions no longer share ordinary
`useState`, so shared state needs [a store](/state). In exchange you get
per-contribution memoisation — see [Performance](/performance).

Reach for the runtime channel when the contribution genuinely is not known up
front — a status bar entry that exists only while a dialog is open, a badge a
row puts up about its own selection, chrome that depends on where in the tree
it happens to be mounted. A feature stays one subtree, so its parts share
ordinary state, and installing it is mounting it. You pay for it with SSR.

## Mixing them

Both channels feed the same host and rank on the same `order`, so an
application can use both — even in the same slot.

```tsx twoslash
// [!include ~/snippets/registry-guide.tsx:mixed]
```

When a declared contribution and a fill share one `order`, the declared one
comes first: it is the one the server also rendered, so the position it already
occupies in the markup is the position it keeps. See [Ordering](/ordering).

Mixing is a supported shape, not a migration step. A slot that is
server-rendered from the plugin list and also accepts a live fill is exactly
what the pages-router [example](/examples) ships.
