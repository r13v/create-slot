# Политики slot

> Статус: **Частично закрыто в v4** (ADR 0004): `disable` вошёл в `ResolveOptions`. limit/allow/deny отклонены — кросс-канальный limit ломает SSR-детерминизм; политики выражаются userland-функциями над `Resolution`.

## Проблема

Не каждый slot способен безопасно принять произвольное число contributions от
любых плагинов. Toolbar имеет ограниченное место, логотип должен иметь одного
владельца, а внутренний slot не должен расширяться сторонними plugins. Сейчас
такие ограничения существуют только как соглашения приложения.

## Предложение

Разделить контракт slot и политику конкретного приложения:

```tsx
const Logo = defineSlot<LogoProps>("acme/logo/v1", {
  cardinality: "one",
  optional: true,
  visibility: "internal",
})

;<PluginProvider
  plugins={plugins}
  policies={{
    "acme/toolbar/v1": {
      max: 5,
      maxPerPlugin: 1,
      allowPlugins: ["core", "pricing"],
    },
  }}
/>
```

Контракт задаёт свойства, одинаковые для всех приложений. Provider policy
задаёт локальные ограничения интегратора.

## Поведение нарушений

Resolved index детерминированно принимает первые подходящие contributions в
итоговом порядке. Остальные не рендерятся и передаются в
`onPolicyViolation` вместе с причиной, slot и contribution ID.

Validation может сделать то же нарушение ошибкой CI. Runtime по умолчанию не
должен обрушать всё приложение из-за одного лишнего contribution.

## Границы

- Политики защищают UI-контракт, но не являются security boundary.
- Они не заменяют серверную авторизацию.
- `cardinality: "one"` не превращает slot в router и не выбирает владельца
  случайно.
- Условия на React state и hooks не входят в policy API.

## Критерии готовности

- Одни и те же данные дают одинаковый результат на сервере и клиенте.
- Каждое отклонение имеет наблюдаемую причину.
- Allowlist и лимиты работают на уровне plugin и contribution ID.
- Внутренний slot нельзя расширить внешним plugin без явного разрешения.
- Placeholder корректно отображается, если политика отклонила все entries.
